CI/CD 调优篇：Git、Maven、Jenkins、GitLab CI/CD、Docker、K8s 与 Ansible

发表于 2025-06-12 | 分类于 调优 ， DevOps

流水线缓存与并行化边界

缓存只保存可重建的依赖和中间产物，不缓存密钥、部署凭据和未验证的构建结果。Maven、npm、Docker layer cache 要按锁文件和基础镜像摘要分 key；缓存命中后仍执行校验。测试按单元、集成、端到端分层并行，集成测试依赖临时数据库或 Testcontainers。

# 发布前的最小门禁示例
mvn -B -T 1C verify
trivy image --exit-code 1 --severity HIGH,CRITICAL "$IMAGE"
cosign verify "$IMAGE"
kubectl apply --server-side --dry-run=server -f k8s/

发布策略与供应链

Deployment 使用 RollingUpdate 时设置 maxUnavailable=0 和适度 maxSurge，readinessProbe 必须验证真实依赖可用。灰度期间比较错误率、p95、资源使用和业务转化率，自动回滚不能只看 Pod 是否 Running。Ansible Vault、GitLab protected variables 和 OIDC 短期凭据优于长期明文 token。

不要在 CI 日志打印环境变量、云凭据或完整构建命令中的 token；依赖升级必须经过锁文件变更审查和漏洞报告。

CI/CD 调优目标是更短反馈时间和可重复发布。缓存依赖与镜像层、并行化测试、限制构建资源，并将 SBOM、签名和漏洞门禁纳入流水线。

APM 调优篇：SkyWalking、ELK Stack、Prometheus 与 Grafana

发表于 2025-04-17 | 分类于 调优 ， 可观测性

高基数、采样和存储成本

APM 系统最容易被高基数标签和无边界日志拖垮。指标标签禁止使用 userId、订单号、完整 URL 和 requestId；这些字段放到日志或链路 span 的受控属性中。SkyWalking 采样率按服务重要性分级，错误、慢请求和关键交易可以提升采样，正常成功链路按比例采样。

# Prometheus 查询：识别高基数指标
topk(20, count by (__name__)({__name__=~".+"}))
# 查看目标抓取与样本增长
prometheus_tsdb_head_series
rate(prometheus_tsdb_head_samples_appended_total[5m])

告警要可行动

告警使用多窗口、燃尽率或 RED/USE 指标，避免单个瞬时点触发。每条告警包含影响范围、查询链接、runbook、负责人和自动恢复动作。日志、指标和链路使用同一 traceId，但不要把完整请求体写入日志；敏感字段在采集端脱敏。

观测系统故障时业务仍应可用：Agent 上报失败要丢弃或限队列，Filebeat/OTel 缓冲达到阈值要降级，Prometheus remote_write 失败不能阻塞本地抓取。

可观测性系统也会消耗 CPU、网络和存储。采用采样优先、标签受控、冷热分层，保证故障高峰仍能查询关键链路。

分布式框架调优篇：Spring Cloud Alibaba、Nacos、Seata、Gateway、OpenFeign、Sentinel、Sharding-Proxy 与 XXL-JOB

发表于 2025-03-06 | 分类于 调优 ， 分布式

超时、重试与熔断必须成组设计

重试只有在调用可幂等、剩余时间预算充足、下游没有整体过载时才有价值。每一跳超时应递减：网关总预算大于应用预算，应用预算大于 Feign/数据库预算；重试引入的放大倍数要纳入下游容量。Sentinel 降级响应必须是业务可接受的默认值，而不是空响应。

# 建议统一记录的远程调用字段
traceId, targetService, route, timeoutMs, retryCount,
statusCode, exceptionType, elapsedMs, fallbackName

注册中心与任务调度运维

Nacos 配置变更使用命名空间、灰度 Data ID 与回滚版本，避免全量推送错误参数。Seata 的全局锁等待和 undo_log 膨胀需要看板与清理策略。XXL-JOB 任务需要幂等业务键、执行超时、分片参数和告警收敛，禁止把长事务任务直接放入调度器线程。

分布式调优首先控制重试和连接总量，把超时、重试、熔断、限流、注册中心和任务调度纳入容量预算，避免重试风暴。

框架调优篇：Spring、Spring Boot、MyBatis/Plus、JPA、Netty 与 Sharding-JDBC

发表于 2025-01-16 | 分类于 调优 ， 框架

线程池隔离与超时传播

Spring 的 @Async、Web MVC 异步、消息消费和 Netty 业务执行器应分池，且每个线程池都要有队列上限、拒绝策略和指标。没有上限的队列会把过载转化为长尾延迟和堆内存膨胀。超时从入口传递到数据库和远程调用，避免上游已放弃、下游还持续执行。

# application.yml 示例：线程池必须受限
spring:
  task:
    execution:
      pool:
        core-size: 8
        max-size: 32
        queue-capacity: 500
      shutdown:
        await-termination: true

ORM 与分片边界

MyBatis/JPA 的首要性能问题通常是 N+1、无界分页和一次性加载大对象图。为列表接口设计 DTO 查询，限定字段和单页大小；写入采用批处理且控制事务批次。Sharding-JDBC 只有携带分片键时才会路由到少量分片，缺失分片键的查询应被审计或在业务层拒绝。

以 Spring Boot 3.x + Java 21 为例，从线程模型、连接池和序列化边界入手；所有超时小于上游网关并为重试预留预算。

OpenResty 调优篇：事件模型、缓存与 LuaJIT

发表于 2024-12-12 | 分类于 调优 ， 网关

事件循环的边界

每个 worker 处理大量非阻塞连接，但一段阻塞 Lua、DNS 查询、磁盘 I/O 或过重正则都可能拖慢该 worker。请求路径只做鉴权、路由、缓存和轻量转换；复杂计算交给上游服务或异步队列。Lua 代码使用 cosocket，避免直接调用阻塞系统命令。

# 快速检查配置与连接状态
openresty -t
curl -s http://127.0.0.1/nginx_status
tail -f /var/log/nginx/access.log
tail -f /var/log/nginx/error.log

缓存正确性

缓存键必须包含影响响应的租户、语言、认证状态和必要请求头；缓存响应不要误包含 Set-Cookie。对回源失败设置 stale-while-revalidate 或短暂 stale 响应能提升可用性，但敏感数据和权限变更接口必须主动失效。限流 key 用用户、IP 或 API 维度组合，避免 NAT 场景误伤。

OpenResty 基于 Nginx 事件循环和 LuaJIT。调优关键是 worker、连接上限、proxy 缓冲和 Lua 共享字典；请求路径禁止阻塞 I/O。

Tomcat 调优篇：线程池、连接器与会话管理

发表于 2024-11-07 | 分类于 调优 ， Web容器

线程池必须与下游一起计算

Tomcat 线程并不是越多越好。若请求大部分时间等待数据库，400 个 Tomcat 线程可能同时抢 32 个数据库连接，排队会把超时放大。线程数、HikariCP、HTTP 客户端连接池与下游限流必须共同配置，并让最外层网关超时大于应用超时、应用超时大于下游超时。

# 发生卡顿时采集三次线程栈，间隔 10 秒
jcmd <pid> Thread.print -l > /tmp/thread-1.txt
sleep 10
jcmd <pid> Thread.print -l > /tmp/thread-2.txt
# 观察 BLOCKED、WAITING 和同一调用栈持续存在的线程

连接、上传与慢客户端防护

maxConnections 受文件描述符和内存限制，必须与 Linux nofile 一起验证。上传接口单独设置大小、读取超时和并发限制；长轮询、SSE、WebSocket 不应与普通同步请求争夺同一线程池。AccessLog 应记录请求耗时和状态码，便于识别单 URL 的尾延迟。

Tomcat 10.1 调优遵循“线程数匹配下游容量”。先用 NIO/NIO2 与共享线程池，再依据 p99、队列和 GC 调整 maxThreads。

MongoDB 调优篇：WiredTiger 缓存、索引与连接池

发表于 2024-10-03 | 分类于 调优 ， 数据库

工作集、索引和缓存关系

MongoDB 性能首先取决于活跃数据和活跃索引能否驻留在 WiredTiger 缓存与文件系统缓存中。缓存不足时会出现频繁页读取和尾延迟升高；缓存过大又会挤压操作系统页缓存。通过慢操作、执行计划和 WiredTiger cache 指标判断，而不是仅按内存百分比配置。

db.orders.aggregate([
  {$match:{tenantId:1}},
  {$indexStats:{}}
])
db.currentOp({active:true, secs_running:{$gt:5}})
db.serverStatus().opcounters

副本集与读写语义

writeConcern: {w: "majority"} 提升故障下的数据安全，但延迟会受最慢投票节点影响；读偏好 secondary 可能读到旧数据。订单状态、库存等强一致读取留在 primary 或使用 afterClusterTime；报表、搜索候选等可接受最终一致的读再走副本。

索引上线后观察写入延迟、索引尺寸、查询扫描文档数和复制延迟至少一个业务周期。未使用索引的删除要先确认不是低频任务或未来索引。

MongoDB 7.x 的 WiredTiger 已较稳健，调优重点是工作集、索引选择性、写关注级别和连接池。副本集先保证多数派写入，再讨论吞吐。

Kafka 调优篇：吞吐、可靠性与消费者滞后

发表于 2024-08-29 | 分类于 调优 ， 消息队列

分区与副本容量计算

分区数应以目标吞吐、单分区可持续吞吐、消费者并行度和恢复时间共同计算。扩分区会改变 key 到分区的映射，因此依赖同 key 全局顺序的主题需预留分区。三副本、min.insync.replicas=2 与 acks=all 是高可用常用组合，但要为复制流量和故障恢复预留磁盘空间。

# 识别滞后与副本异常
kafka-consumer-groups.sh --bootstrap-server broker:9092 --describe --group your-group
kafka-topics.sh --bootstrap-server broker:9092 --describe --topic your-topic

消费者稳定性

Consumer 处理时间必须小于 max.poll.interval.ms；耗时任务应拆成小批或转给工作线程并正确提交 offset。不要因为滞后就无上限增加消费者，分区数才是并行度上限。重平衡频繁时检查部署滚动策略、session timeout、GC 停顿和外部依赖耗时。

不要把消息保留策略当作备份。Kafka 的 retention 受时间和磁盘阈值影响，合规或审计数据应同步到对象存储或独立归档系统。

Kafka 3.x 调优同时满足吞吐与交付语义：Broker 顺序写和页缓存，Producer 批量/压缩，Consumer 拉取与提交。

Elasticsearch 调优篇：堆内存、分片与刷新策略

发表于 2024-07-25 | 分类于 调优 ， 搜索

分片不是越多越好

主分片一旦创建不能直接缩小，因此应按生命周期内的数据量规划，而不是按当天数据量规划。时间序列优先 Data Stream + ILM，按 rollover 的文档数、大小或时间切分；查询跨越过多小分片会放大协调节点 CPU、堆和网络开销。

# 查看分片大小、段数量与拒绝请求
GET _cat/shards?v=true&bytes=gb
GET _cat/segments?v=true
GET _nodes/stats/thread_pool?filter_path=nodes.*.thread_pool.write

查询保护与映射治理

动态映射只适合受控字段，日志中的任意 JSON 字段可能导致 mapping explosion。为关键词字段选择 keyword，为全文选择 text；不要对不聚合、不排序的字段启用不必要的 doc_values。查询层限制时间范围、聚合桶数和深分页，异常请求通过网关或应用侧提前拒绝。

症状常见根因优先动作
写入 rejectedBulk 并发过高、磁盘慢客户端退避并减小批次
查询慢分片过多、深聚合缩小范围、预聚合
堆高fielddata、映射膨胀修正映射并限制字段

Elasticsearch 8.x 受 JVM 堆、磁盘 I/O、分片数量和查询模式共同影响；经典基线是堆不超过 31GB、约占物理内存一半。

RocketMQ 调优篇：刷盘、堆外与消费者并发

发表于 2024-06-20 | 分类于 调优 ， 消息队列

Topic、队列与存储规划

队列数决定生产与消费并行度，但过多队列会增加文件句柄、元数据和重平衡成本。按目标峰值 TPS、单消息大小、消费耗时和副本能力规划队列，并将顺序消息的 sharding key 与队列映射稳定下来。Topic 权限应默认关闭自动创建，避免拼写错误产生无人消费的新 Topic。

# 关注消费堆积和 Broker 存储状态
mqadmin consumerProgress -n namesrv:9876
mqadmin topicStatus -n namesrv:9876 -t YourTopic
mqadmin clusterList -n namesrv:9876

可靠性与重试边界

发送成功不等于业务成功。Producer 使用唯一业务键并开启幂等处理，Consumer 必须能重复消费；失败消息进入重试主题前要记录失败原因、重试次数和下一步操作。超过最大重试后进入死信队列，告警和人工补偿流程必须可演练。

上线前压测应覆盖：大消息拒绝、Broker 重启、主从切换、磁盘接近阈值和消费者处理变慢。验收指标包括可恢复时间、堆积恢复速度与重复消费正确性。

RocketMQ 5.x 调优围绕 CommitLog 顺序写、PageCache、副本策略和消费并发；Broker 磁盘优先 NVMe/高性能云盘并与系统日志隔离。
