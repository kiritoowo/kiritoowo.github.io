Redis 调优篇：内存淘汰、持久化与高并发连接

发表于 2024-05-16 | 分类于 调优 ， 中间件

内存模型与淘汰策略选择

先区分 Redis 是缓存、会话、排行榜还是主数据副本。缓存可容忍逐出时使用 allkeys-lfu；仅对带 TTL 的键逐出时才选择 volatile-*。每个业务键必须定义 TTL、最大值和失效后的降级行为，避免没有过期时间的 key 挤占热数据。

# 采集内存碎片、大 key 和复制压力
redis-cli info memory
redis-cli memory stats
redis-cli --memkeys
redis-cli info replication
redis-cli latency doctor

客户端连接与故障切换

连接池上限要乘以实例数计算，不要让每个应用实例创建数百条空闲长连接。读写分离要接受复制延迟，不能把强一致读路由到副本。哨兵或 Cluster 切换时客户端需刷新拓扑并设定合理的 connect/read timeout，业务侧仍需具备缓存未命中回源保护。

异常优先检查处理方向
延迟尖刺slowlog、fork、AOF rewrite、交换分区拆分大 key、安排重写窗口
频繁逐出maxmemory、TTL、内存碎片扩容或缩短无效数据生命周期
主从延迟网络、repl backlog、输出缓冲减少大命令和复制阻塞

Redis 7.x 调优重点是避免阻塞命令、控制内存水位、明确 AOF/RDB 安全目标，并让连接池与超时可观测。

MySQL 调优篇：InnoDB、连接池与慢查询治理

发表于 2024-04-10 | 分类于 调优 ， 数据库

先识别工作负载，再设置参数

OLTP、高并发读、批处理导入和分析型查询的参数目标不同。OLTP 优先稳定事务延迟与锁等待；导入任务优先顺序 I/O 和批量提交；分析查询则需要避免它们抢占线上 Buffer Pool。将批任务安排在低峰，或放到只读副本，而不是为一次导入长期放宽持久化参数。

# 最耗时语句、索引使用和锁等待
SELECT digest_text, count_star, avg_timer_wait
FROM performance_schema.events_statements_summary_by_digest
ORDER BY sum_timer_wait DESC LIMIT 10;
SELECT * FROM sys.schema_unused_indexes;
SELECT * FROM sys.innodb_lock_waits;

索引变更与事务边界

索引前先确认过滤选择性和返回列，避免为了覆盖索引写入过宽索引。大表 DDL 使用 Online DDL 或 gh-ost、pt-online-schema-change，并在副本先演练。事务应短小，避免把 RPC、文件上传和用户交互包在事务中；批量更新用主键范围分段，控制单批行数以降低 undo 与锁持有时间。

提交参数的最低验收集合：慢查询 Top 10、Buffer Pool 读命中、行锁等待、redo checkpoint age、主从延迟以及磁盘 fsync p99。

MySQL 8.0 调优围绕 InnoDB Buffer Pool、redo/binlog 持久化、连接池和慢 SQL 证据展开，示例面向 32GB 专用节点。

JVM 调优篇：通用参数与 ParallelGC、G1GC、ZGC 选择

发表于 2024-02-22 | 分类于 调优 ， JVM

对象分配比 GC 参数更重要

GC 调优的首选手段不是增加堆，而是减少无效分配。排查 JSON 字符串拼接、重复反序列化、大集合全量加载、临时 byte[] 和无限缓存。先从 GC 日志中确认分配速率、晋升速率与 Full GC 原因，再用 JFR 或 async-profiler 定位分配热点。

# JDK 21：持续记录 5 分钟事件
jcmd <pid> JFR.start name=allocation settings=profile duration=5m filename=/tmp/allocation.jfr
jcmd <pid> GC.heap_info
jcmd <pid> VM.native_memory summary

收集器选择与验收

现象优先行动不要直接做的事
Young GC 频繁检查分配速率、缓存与批量大小盲目增大 Xmx
Mixed GC 长检查老年代增长和大对象手工固定年轻代比例
Full GC看 GC cause、元空间、直接内存只更换收集器
p99 抖动关联 safepoint、CPU 抢占和 I/O只看平均 GC 时间

验收应保留压测前后的吞吐、p50/p95/p99、GC 总暂停、最大暂停、CPU 使用率与容器 RSS。若 ZGC 改善停顿却明显增加 CPU，应根据业务 SLO 而非单项指标决策。

以 JDK 21 LTS 为例，先设堆边界、GC 日志和 OOM 行为，再按停顿目标选收集器；容器预算需包含堆外与线程栈。

服务器参数调优篇：Ubuntu LTS 初始化、安全与内核基线

发表于 2024-01-18 | 分类于 调优 ， 服务器

容量规划与变更顺序

调优不是把所有上限调大。先依据连接数、文件描述符、网卡带宽、磁盘 IOPS 和内存水位建立容量表，再定位最先饱和的资源。应用最大连接数、反向代理连接数、数据库连接池和 nofile 必须来自同一份预算；否则应用看似仍有线程，实际已被内核队列或端口耗尽限制。

阶段动作通过条件
基线连续采集 24 小时 CPU、内存、网络、磁盘、连接数明确高峰 QPS 与 p99
压测逐级提高并发，单次只改一个参数组无连接拒绝、无明显重传
灰度先 5% 流量、观察一个高峰周期错误率和 p99 不劣化
回滚保留旧 sysctl 文件与服务限制可在分钟级恢复

安全基线细节

SSH 只允许密钥登录并限制来源网段；管理面端口不要和公网业务端口混用。Fail2ban 的封禁仅用于减缓暴力破解，不能替代安全组和身份认证。对外服务应启用自动安全更新，并在维护窗口验证内核升级后的驱动、容器运行时和 eBPF 监控兼容性。

# 查看有效限制与连接状态
systemctl show your-service -p LimitNOFILE
ulimit -n
ss -s
cat /proc/sys/fs/file-nr
# 查看半连接与重传
netstat -s | grep -E 'listen|retransmit|SYN'
不要启用已废弃或风险不明确的网络参数，例如 tcp_tw_recycle。NAT、移动网络和多出口环境下，它会造成正常连接被错误丢弃。

Ubuntu 24.04 LTS（兼容 22.04 LTS）生产基线，覆盖初始化、漏洞扫描、UFW/Fail2ban、防火墙、文件句柄、交换分区与 TCP 栈。
